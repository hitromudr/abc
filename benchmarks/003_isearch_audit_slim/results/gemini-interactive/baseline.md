# Отчет об аудите кодовой базы проекта `isearch` (Baseline)

## Резюме
Проведен глубокий аудит кодовой базы поисковой системы `isearch`. Выявлен ряд серьезных архитектурных и логических уязвимостей, наиболее критичные из которых связаны с генерацией идентификаторов в векторной базе данных и потенциальной гонкой данных при асинхронном индексировании. Проект в текущем виде не готов к стабильной работе в Production (особенно при перезапусках сервиса и конкурентных запросах).

## Классификация дефектов и уязвимостей

### 1. Критические уязвимости (Угроза потери данных и консистентности)

**1.1. Нестабильные идентификаторы (ID) точек в Qdrant (Утечка/Дублирование)**
- **Локация:** `src/vector_store.py` (метод `upsert`)
- **Проблема:** ID для векторов генерируется с помощью встроенной функции Python `hash()`: `abs(hash(p.get("source_file", "") + p.get("text", "")))`. По умолчанию в Python используется алгоритм SIPHash, который инициализируется случайным seed при каждом новом запуске интерпретатора. Это означает, что при перезапуске сервиса одинаковые фрагменты текста (чанки) получат совершенно другие ID.
- **Последствия:** Инкрементальное обновление и переиндексация полностью ломаются после перезапуска API. Вместо перезаписи (upsert) существующих точек векторная база будет бесконтрольно расти за счет дубликатов, а удаление устаревших чанков станет невозможным или приведет к фантомным записям.
- **Решение:** Использовать детерминированное криптографическое хеширование (например, `hashlib.sha256()`), конвертируя байты в `int` для соответствия требованиям Qdrant к беззнаковым целочисленным ID, либо генерировать стабильные UUID3/UUID5 на основе пути и содержимого.

**1.2. Состояние гонки (Race Condition) при фоновом индексировании**
- **Локация:** `src/main.py` (`index_project_endpoint`), `src/state_manager.py`
- **Проблема:** Эндпоинт `/projects/{project_name}/index` запускает асинхронную задачу в фоне через `BackgroundTasks`. Для одного и того же проекта нет никаких блокировок. Менеджер состояний (`IndexStateManager`) читает и пишет состояние в файл `state.json` обычным `open(..., "w")`.
- **Последствия:** Если вызвать эндпоинт индексации несколько раз подряд для одного проекта (или если это сделают разные пользователи), несколько фоновых потоков начнут параллельно читать и перезаписывать `state.json`, а также отправлять конфликтующие батчи в Qdrant. Это с высокой вероятностью приведет к повреждению (corruption) файла JSON и рассинхронизации локального стейта с векторной БД.
- **Решение:** Внедрить межпроцессные блокировки (например, библиотеку `filelock` для `state.json`) или ограничить запуск индексации на уровне контроллера (проверять через `TASK_STATUS`, не запущена ли уже индексация для данного проекта).

### 2. Высокий риск (Проблемы производительности и лимиты API)

**2.1. Переполнение фильтров Qdrant при инкрементальном обновлении (Denial of Service)**
- **Локация:** `src/vector_store.py` (методы `get_documents_by_source` и `delete_points_by_source`)
- **Проблема:** Для фильтрации и удаления точек по конкретным файлам динамически собирается гигантский OR-список: `should=[FieldCondition(key="source_file", match=MatchValue(value=file)) for file in source_files]`.
- **Последствия:** При индексации крупных проектов, где количество измененных или удаляемых файлов может достигать тысяч, генерируется огромный payload фильтра. Это может легко превысить лимиты gRPC/HTTP запросов Qdrant, вызвать Timeout или обрушить базу данных из-за нехватки памяти при парсинге запроса.
- **Решение:** Выполнять удаление и выборку батчами по 100-200 файлов, либо пересмотреть схему работы с payload-индексами (использовать `MatchAny` вместо длинного списка `should`).

### 3. Средний риск (Логические ошибки и утечки памяти)

**3.1. Пагинация при кластеризации читает не все данные (Ограничение выборки)**
- **Локация:** `src/main.py` (эндпоинт `/projects/{project_name}/clusters`)
- **Проблема:** Метод получает все векторы коллекции вызовом `vector_store.client.scroll(..., limit=10000)[0]`, запрашивая только первую страницу.
- **Последствия:** Если в проекте сгенерировано более 10 000 чанков (что стандартно для средних репозиториев), кластеризация просто проигнорирует оставшуюся часть кода без каких-либо предупреждений, выдавая искаженный граф и неполные кластеры. Пагинация через `next_page_offset` не реализована.
- **Решение:** Обернуть вызов `scroll` в цикл `while`, аналогично тому, как это корректно сделано в методе `get_documents_by_source`.

**3.2. Ошибка применения Keyword Boosting в поиске**
- **Локация:** `src/main.py` (эндпоинт `/projects/{project_name}/search`)
- **Проблема:** Алгоритм бустинга (`top_hit.score = min(1.0, top_hit.score + boost_factor)`) применяется *только к первому элементу* в уже сгруппированном по файлам списке (`group.hits[0]`). Кроме того, этот буст применяется *после* того, как массив `grouped_list` был сформирован, но *до* его финальной сортировки.
- **Последствия:** Документация или код получают приоритет только для своего верхнего сниппета, в то время как остальные совпадения внутри файла остаются с низким скором. 
- **Решение:** Применять буст-фактор ко всем найденным `hits` еще на этапе их получения из Qdrant (или в цикле `for hit_data in results`), до начала группировки.

**3.3. Утечка памяти в словаре TASK_STATUS**
- **Локация:** `src/main.py`
- **Проблема:** Глобальный In-Memory словарь `TASK_STATUS` накапливает данные о статусах всех запущенных задач индексации, но в коде нет механизма их удаления.
- **Последствия:** При долгом времени работы API (uptime) и частой индексации память приложения будет постепенно утекать.
- **Решение:** Добавить периодическую очистку завершенных задач по TTL (например, удалять задачи старше 24 часов) или использовать внешнее хранилище вроде Redis.
